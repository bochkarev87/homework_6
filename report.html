1. Executive summary

I built the required user–movie graph from positive training interactions, implemented global PageRank and seeded Personalized PageRank (PPR) with TensorFlow.js, and evaluated popularity, global PageRank, PPR and matrix factorization (MF) on one shared test cohort. All seven assignment stubs are implemented, all 12 self-checks pass, and every reported propagation run converged below the L1 tolerance of 1e-6.

2. Related work

This project combines link analysis, personalized search and latent-factor collaborative filtering. Brin and Page introduced PageRank as a global authority score for web pages (Brin and Page 1998). Our global PageRank baseline applies the same fixed-point update to a bipartite user–movie graph. Because a walk alternates between user and movie nodes, the global stationary mass is driven by degree and connectivity rather than by one user's history; it is therefore best read as a graph-smoothed popularity signal, not as a personalized recommender.

Jeh and Widom introduced personalized PageRank, which replaces the uniform restart with a distribution concentrated on a seed (Jeh and Widom 2003). Our PPR uses the same random-walk with restart, with a one-hot restart at the target user. We compute it exactly by batched power iteration on the 2,554-node graph rather than by precomputed basis vectors or approximate top-k propagation. The algorithmic contribution here is therefore an implementation and evaluation study, not a new PPR variant: the batched path makes 861 user-specific runs practical in the browser, and its output is checked against the single-seed implementation.

Matrix factorization represents users and movies by latent factors learned from observed ratings (Koren, Bell and Volinsky 2009). Our MF follows the week-5 explicit-rating model: a 16-dimensional dot product plus the global training mean, trained with RMSE loss and Adam. This differs from pairwise ranking objectives such as BPR, which optimize the order of positive and negative items directly (Rendle et al. 2009). That objective mismatch is one reason to expect weaker Recall@10 from an RMSE-trained model, and it is why the report treats MF as a predicted-rating shelf rather than as a like-for-like ranking competitor.

MovieLens 100K is the standard benchmark used here (Harper and Konstan 2015). Published MovieLens results are not directly comparable to our numbers because they use different splits, candidate sets and ranking protocols. We therefore compare only methods trained and evaluated inside this repository on the same 861-user cohort, and we report the exact exclusion rules rather than matching a published leaderboard.

Positioning. The assignment is not a novel recommendation algorithm. Its contribution is a reproducible browser harness that compares four ranking signals under one cohort, an exact batched PPR implementation validated against a single-seed reference, and a disclosed correction to the starter MF regularizer.

4. Implementation and verification

4.1 Graph and propagation

Users occupy node indices 0..nUsers−1 and movies follow, so no padding node enters the graph or the candidate pool. For each positively rated training pair, the user row is normalized over that user's positive movies and the movie row over the users who rated it positively. The propagation uses the two off-diagonal blocks R and RT rather than materializing a dense 2,554 × 2,554 matrix.

Dangling mass is not discarded: zero-degree rows contribute their mass to the restart distribution v, using the same rule in global PageRank and PPR. A run stops when the L1 difference between consecutive distributions is below 1e-6, or at 500 iterations; the iteration cap is never treated as proof of convergence.

PPR for evaluation is computed once per (graph, alpha, split) for the whole cohort in a single batched TensorFlow.js propagation, then reused for each user's Top-10. This keeps the main propagation in tensor operations and avoids repeating a per-user walk 861 times. The batched path was checked against the single-seed reference: at alpha 0.85 the two ran 94 and 91 iterations and differed by at most 3.96e-9 in movie scores, which is float32 noise.

4.2 MF reference

MF keeps the week-5 scoring definition: dot product of 16 learned factors plus the global training mean, used as a predicted rating. It is not converted into a probability and its scores are never compared numerically with PPR walk probabilities. Training uses Adam, learning rate 0.01, regularization 0.05, batch size 512, 30 epochs and a fixed seed; the best validation-RMSE checkpoint is epoch 4 with validation RMSE 0.9779.

Disclosed correction. The starter's L2 term summed over every factor row, which collapsed all embeddings toward zero in the first epoch (validation RMSE stuck at 1.1830, checkpoint 1). I replaced it with the week-5 per-batch mean objective, (sum(u²) + sum(i²)) × reg / batchSize. This changes regularization only; the scoring rule and the validation-checkpoint rule are unchanged.

4.4 Hand-computed propagation check

To check the code against arithmetic rather than only against itself, take the four-node reference graph with p0 = [0.25, 0.25, 0.25, 0.25] and alpha = 0.85. Before restart, A receives C's mass 0.25; B receives half of A's mass, 0.125; C receives half of A plus B plus D, 0.125 + 0.25 + 0.25 = 0.625; D receives nothing. Adding the uniform restart gives p1 = 0.85 × [0.25, 0.125, 0.625, 0] + 0.15 × 0.25, i.e. [0.25, 0.14375, 0.56875, 0.0375].

With the application loaded, this DevTools console call forces one update:

Array.from(pageRank(0.85, {
  transition: REFERENCE_GRAPH.transition,
  maxIter: 1
}).p)
// [0.25, 0.14375001192092896, 0.5687500238418579, 0.03750000149011612]

The code returns the hand-computed vector to float32 precision; the largest coordinate error is 2.4e-8. Running to convergence returns [0.37252694, 0.19582376, 0.39414933, 0.03750000] in 28 iterations with residual 9.54e-7, within 1.6e-7 of the supplied reference vector and below the 1e-6 tolerance. This is the requested hand-computed check: it verifies one propagation step and the fixed point, not the full 861-user evaluation.

7. Business and algorithmic analysis

Should the platform keep MF, replace it with PPR, or use both?

Use both, in different sections. PPR should power the primary discovery row because it has the strongest retrieval evidence: Recall@10 0.1122 versus 0.0797 for global PageRank, 0.0760 for popularity and 0.0312 for MF on the shared 861-user cohort. It is also genuinely user-conditioned: changing only the restart user replaced all ten baseline titles, while changing only alpha retained seven. MF should remain as a predicted-rating shelf, not as the main discovery row: its retrieval is weaker, but its lists are much less popularity-driven (mean training popularity 94.3 versus 244.2 for PPR) and only 4/10 titles overlap with PPR for the two users.

The lists make the distinction concrete. User 1's PPR row starts with Fargo (1996) (Crime; Drama; Thriller), while the MF shelf starts with The Wrong Trousers (1993) (Animation; Comedy). User 2's PPR row starts with Return of the Jedi (1983) (Action; Adventure; Romance; Sci-Fi; War), while the MF shelf starts with Persuasion (1995) (Romance). These are different recommendation intents, not two rankings of one score.

The proposed sections have distinct purposes. The PPR row is a graph-based discovery surface: “users with your positive history also connect to these movies.” The MF row is a rating-style shelf: “movies the fitted model predicts you would rate highly.” Showing both gives the platform a recall-oriented list and a rating-oriented list without pretending that one score scale is the other. This is a hypothesis supported by offline retrieval and list overlap, not a demonstrated engagement gain.

Online experiment before rollout

Run a user-level randomized controlled trial for two weeks with three arms: (A) PPR discovery row only, (B) MF predicted-rating row only, (C) both rows in their proposed sections. Assign each user by a stable hash of user ID to one arm; keep assignment fixed for the experiment so a user does not cross arms, and analyze by intention to treat. This avoids contamination between recommender variants.

  • Primary outcome: 7-day qualified watch-through rate on the recommendation surface (or click-through rate if watch completion is not observable), measured per assigned user, not per impression.
  • Guardrails: catalog coverage and intra-list diversity; p95 recommendation latency; hide/report/complaint rate; and a minimum popularity floor so the discovery row does not collapse into obscure titles.
  • Decision rule: ship both only if arm C improves the primary outcome over the better single-row arm without breaching a guardrail. Pre-register the metric definitions and the analysis window before launch; do not choose the winner from a post-hoc subgroup.

Offline Recall@10 cannot establish current-session intent, viewing completion, satisfaction, retention or revenue. It also cannot tell us whether a less popular list is a better discovery experience or simply a worse match. The online experiment, not the offline table, must decide deployment.

8. Limitations and disclosures

  • The split is chronological within each user, not globally time-consistent. MovieLens records rating times, not viewing sessions.
  • Evaluation is warm-user only; users without positive training edges are excluded, so no cold-start claim is made.
  • The 13 relevant test IDs absent from the training candidate pool cannot be retrieved by any method and are reported rather than hidden.
  • MF and PPR use different validation objectives (RMSE vs Recall@10), so their test recalls are descriptive. The MF L2 correction is disclosed in section 4.2; without it the reference collapsed to the global mean.
  • Popularity is counted from training ratings only and is descriptive, not a platform impression count.
  • Timings come from one headless Chrome/WebGL run on the stated GPU and are not compared across devices.
  • The unmodified AI-session export is an administrative submission step and is not embedded in this report.

What this work gave me. The main result is not that PPR is newer or automatically better. It is that a graph method can be compared with two baselines and a previous model under one shared cohort, and that the comparison can support a specific deployment choice. I now understand alpha as an exploration–restart trade-off rather than a quality knob: it has to be selected on validation, and a larger value is not automatically better. I also understand why MF and PPR should not share a score scale: one predicts ratings, while the other ranks graph proximity. Finally, the offline numbers justify a hypothesis, not a rollout; the proposed A/B test is the next step before claiming engagement gains.
